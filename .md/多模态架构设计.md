## 一、文档定位

这份文档只描述**当前项目真实落地的多模态数据模型**，以及它与任务系统、Provider 适配层、Agent/画布系统的关系。

它不再维护“理想化的全量端口类型系统”。那套方案曾经存在于早期设计里，但当前仓库里的真实实现已经收口为更小、更稳定的形态：

1. 同步对话链路以 `MultiModalMessage` 为核心。
2. 长耗时生成链路以 `async_tasks.input_data / output_data` 为核心。
3. 画布节点、Agent、执行器之间并没有共享一套“通用多模态端口协议”。

这个收口是刻意的。先把运行时真相写清楚，比继续维护一个没有完全落地的大而全协议更重要。

## 二、当前真实模型

### 2.1 `apps/web/types/multimodal.ts`

当前项目内真正生效的多模态类型只有两层：

```ts
export type ContentPart =
  | { type: 'text'; text: string }
  | { type: 'image_url'; image_url: { url: string } }

export interface MultiModalMessage {
  role: 'system' | 'user' | 'assistant'
  content: string | ContentPart[]
}
```

这意味着当前同步消息主链支持的是：

1. 纯文本消息
2. 文本 + 图片混合消息
3. 以 OpenAI 兼容消息格式为中心的多模态输入

当前**没有**在这个类型层里统一承载：

1. 视频
2. 音频
3. 通用文件
4. 画布端口兼容规则

### 2.2 为什么会收口成这样

因为当前运行时里，多模态其实分成了两类问题：

1. **同步理解类输入**
   主要是文本和图片，直接喂给聊天/理解模型。
2. **异步生成类输出**
   图片、视频、音频主要通过 `tasks/service.ts` 和 Provider 处理器流转，不通过 `MultiModalMessage` 在前端全链条传递。

也就是说，当前代码把“理解输入”和“生成输出”拆成了两条不同的现实路径。

## 三、当前多模态分层

### 3.1 同步消息层

职责：

1. 服务于 LLM/Agent/解释类接口
2. 对齐 OpenAI 兼容消息结构
3. 保持最小可移植成本

当前适用位置：

1. `apps/web/types/multimodal.ts`
2. 文本/图片理解类 Provider 调用
3. Agent 相关提示词与结构化推理入口

### 3.2 任务输入输出层

职责：

1. 服务于图片/视频/音频长任务
2. 承载生成参数、运行时元数据、输出文件地址
3. 与计费、重试、编排状态绑定

当前适用位置：

1. `apps/web/lib/tasks/service.ts`
2. `apps/web/db/schema.sql` 的 `async_tasks`
3. `apps/worker/src/workflows/*`
4. `apps/worker/src/cron/*`

这条链路的真实载体不是 `MultiModalMessage`，而是：

1. `input_data`
2. `output_data`
3. `diagnostics_data`
4. R2 输出文件

### 3.3 画布节点层

职责：

1. 管理节点类型、节点配置、执行顺序
2. 决定某个节点接什么模型、走同步还是异步
3. 通过节点 schema 和执行器约定驱动工作流

当前现实是：

1. 画布层没有一套完整、统一、强约束的多模态端口协议文档真相源
2. 节点能力更多由节点类型、Provider、任务类型和执行器共同决定
3. “端口类型系统”不是当前主运行时的硬核心，而是未来可能补强的抽象层

## 四、与其它子系统的关系

### 4.1 与 Provider 适配层

当前项目已经存在多 Provider 运行时，但多模态能力不是靠一个超大的统一对象吃透所有差异，而是按类别拆开：

1. 文本/图片理解走同步消息结构
2. 图片/视频/音频生成走任务处理器与异步编排

这比“强行用一个万能消息类型装下所有 Provider”更符合当前仓库现实。

### 4.2 与异步任务系统

当前多模态输出最重的真实场景是：

1. `image_gen`
2. `video_gen`
3. `audio_gen`

这些任务由 `apps/web/lib/tasks/service.ts` 统一编排，并具备：

1. `platform / user_key` 双执行模式
2. `legacy_queue / workflow` 双编排模式
3. 冻结 / 确认 / 退款计费链
4. 输出文件落 R2

因此项目里真正复杂的“多模态”问题，当前已经迁移到**任务运行时**，而不是前端消息类型。

### 4.3 与 Agent 工作流系统

Agent 当前已经成为运行时现实。它消费的是：

1. 画布摘要
2. 节点结构
3. 任务与执行状态
4. 模型选择上下文

Agent 会间接操作多模态工作流，但它本身并不依赖一个独立的“全能多模态协议层”。它依赖的是：

1. 节点 schema
2. 画布摘要
3. 结构化 operation plan
4. 现有执行链

## 五、当前设计结论

### 5.1 现状判断

当前项目的多模态架构不是“缺失”，而是**收口**：

1. 消息理解层保持极简
2. 生成任务层承担复杂度
3. 画布层保持节点驱动

这是一个务实的选择。

### 5.2 当前好处

1. 同步消息结构简单，兼容性高
2. 异步生成复杂度被隔离在任务系统
3. Provider 差异不会强行污染前端类型层
4. Agent、计费、Worker、R2 可以围绕任务系统自然协作

### 5.3 当前限制

1. 没有统一的视频/音频/文件消息协议
2. 画布连线兼容规则没有形成主文档真相源
3. 节点输入输出能力更多依赖实现细节，文档抽象仍偏弱
4. 后续如果继续扩模型与节点类型，类型边界可能再次变散

## 六、建议的后续演进

### 6.1 近期不该做的事

当前不建议立刻恢复一个“全量 PortType + accepts + 自动兼容矩阵”的大系统，原因是：

1. 当前运行时主复杂度不在那里
2. 任务系统、Agent、计费、Provider 仍在真实演进
3. 过早抽象容易再次制造纸面协议和运行时现实脱节

### 6.2 更合理的下一步

如果后续要继续演进，多模态应按下面顺序补强：

1. 先补节点能力清单与执行类别映射
2. 再补画布层的输入/输出约束文档
3. 最后才考虑把同步消息层和异步任务层抽象成统一的跨节点协议

### 6.3 推荐目标

更合理的未来终态不是“一个巨大的万能消息对象”，而是三层稳定抽象：

1. `Conversation Message`
   面向 LLM/Agent
2. `Task Payload`
   面向异步生成
3. `Node Capability Contract`
   面向画布编排

这样能让特殊情况自然融入系统，而不是靠大量 if/else 去硬缝。

## 八、结论

当前项目的多模态架构，最本质的事实是：

1. **文本 + 图片理解**已经有稳定类型
2. **图片 / 视频 / 音频生成**已经迁入异步任务主链
3. **画布编排**依赖节点和任务系统，而不是一个尚未完全落地的万能协议

所以这份文档的职责不是继续幻想“应有多完美”，而是把“现在到底怎么工作”写清楚。
