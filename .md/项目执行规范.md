# Nano Banana Canvas - 项目执行规范

> 文档版本：v3.0
> 创建日期：2024-12-24
> 更新日期：2026-05-15
> 职责边界：本文件只维护**当前项目的开发、验证、文档回环与 git 留痕规范**。

---

## 一、文档定位

这份规范不是泛用前端规范，也不是历史迁移说明。

它只解决一个问题：

**在当前这个已经包含画布、Agent、异步任务、账单、身份、Worker 的真实项目里，怎样开发才不把系统做脏、做散、做出不兼容。**

---

## 二、最高原则

### 2.1 先对齐现实，再动手

任何任务开始前，先确认三件事：

1. 当前代码现实是什么
2. 当前主文档写的是什么
3. 两者是否一致

如果不一致，优先修正文档口径或至少明确偏差，再做实现。

### 2.2 单一真相源优先

当前项目里最重要的真相源包括：

1. 工作流状态：`use-flow-store`
2. 异步任务状态：`async_tasks`
3. 账户身份：`SessionActor -> users`
4. 账本：`credit_balances / credit_transactions / subscriptions / billing_orders`
5. Agent 会话状态：`use-agent-store`

开发时不能为了图快，再造一份平行状态。

### 2.3 兼容性优先于“看起来先进”

如果一个实现会让：

1. 现有 API 口径漂移
2. 文档继续失真
3. 主链 store 出现第二真相源
4. Worker / Web / Shared 协议不一致

那它就不是好实现。

## 三、任务执行流程

### 3.1 标准流程

```text
1. 读项目级规则与当前模块文档
2. 读相关代码现实
3. 判断文档是否过期
4. 再做设计 / 修改 / 重构
5. 完成后做验证
6. 更新文档回环
7. 完成 git 留痕
```

### 3.2 当前项目的启动顺序

进入任务时，默认按这个顺序理解上下文：

1. `CLAUDE.md`
2. `.md/项目框架结构.md`
3. `.md/项目规划清单.md`
4. `.md/项目执行规范.md`
5. 当前目录 `CLAUDE.md`
6. 目标文件 L3 头部契约

如果任务涉及旧方案，还要额外看对应 `archive` 文档，但不能直接把 archive 当当前真相源。

## 四、代码与架构规范

### 4.1 模块边界

#### `apps/web`

负责：

1. 页面
2. API Route Handlers
3. 前端状态
4. 业务逻辑主链

不负责：

1. 把长任务后台协同全部塞进页面逻辑
2. 绕开 Worker 和 task service 另起一套编排

#### `apps/worker`

负责：

1. cron
2. workflow orchestration
3. 长任务后台协同

不负责：

1. 复制 web 里的业务真相源
2. 发明新的账户、计费或工作流模型

#### `packages/shared`

负责：

1. 共享协议
2. 共享常量
3. 跨端一致类型

不负责：

1. 承载重量级业务实现
2. 把 web/worker 强耦合在一起

### 4.2 当前重点约束

1. Agent 不得维护平行 workflow JSON
2. Billing 不得绕开账本直接改余额
3. Tasks 不得绕开 `lib/tasks/service.ts` 另起入口
4. 账户资源不得绕开 `SessionActor` 语义直接拼 Clerk 字段
5. archive 方案不得直接当当前实现蓝图

## 五、文档回环规范

### 5.1 哪些变更必须更新文档

以下情况必须视为文档同步触发器：

1. 新增 / 删除 / 移动文件或目录
2. 模块职责变化
3. API 语义变化
4. 真相源位置变化
5. 某个“规划中能力”正式变成运行时现实

### 5.2 三层回环

#### L3：文件头部

业务文件必须维护：

1. `[INPUT]`
2. `[OUTPUT]`
3. `[POS]`
4. `[PROTOCOL]`

#### L2：模块 `CLAUDE.md`

当模块成员变化或职责变化时，更新对应目录的 `CLAUDE.md`。

#### L1：项目主文档

当顶层结构、主链、阶段状态变化时，更新：

1. `CLAUDE.md`
2. `.md/项目框架结构.md`
3. `.md/项目规划清单.md`
4. `.md/项目执行规范.md`

### 5.3 文档写作原则

1. 写当前现实，不写过期设想
2. 写主链，不堆历史流水
3. archive 只存回溯价值，不冒充当前口径

## 六、实现规范

### 6.1 页面与组件

1. 默认优先 Server Component
2. 只有需要浏览器交互时再用 Client Component
3. 高交互复杂逻辑尽量下沉到 `hooks/`、`stores/`、`lib/`

### 6.2 API Route

1. 所有入参必须校验
2. 错误码要走统一语义
3. 不能把业务逻辑全写在 route 里
4. route 更适合做编排与权限边界，核心逻辑下沉到 `lib/`

### 6.3 状态管理

1. 画布态进 `use-flow-store`
2. Agent 会话态进 `use-agent-store`
3. 执行态进 `use-execution-store`
4. 不允许为了局部方便复制全局状态

### 6.4 任务与计费

1. 平台模式扣费必须走 `freeze / confirm / refund`
2. 异步任务必须优先复用 `lib/tasks/service.ts`
3. 与 Worker 协议相关的字段，优先在 `shared` 对齐

### 6.5 身份与权限

1. 业务层优先消费 `SessionActor`
2. 只在需要保护的页面或 API 做显式守卫
3. 不把“登录可同步”误做成“登录才能用产品”

---

## 七、测试与验证规范

### 7.1 最低验证要求

每次任务完成后，至少做以下自检：

1. 语法正确
2. 结构合理
3. 没有明显真相源冲突
4. 文档与实现没有明显断层

### 7.2 当前项目推荐验证顺序

#### 通用

```bash
pnpm lint
pnpm test
pnpm build
```

#### web 单独验证

```bash
pnpm --filter @nano-banana/web lint
pnpm --filter @nano-banana/web test
pnpm --filter @nano-banana/web build
```

#### e2e

```bash
pnpm --filter @nano-banana/e2e test
```

### 7.3 不能伪造验证

1. 没跑测试，不能写“已验证通过”
2. 只做静态检查，就明确说“仅静态检查”
3. 因环境原因没跑，就把原因写清楚

---

## 八、Git 留痕规范

### 8.1 基本要求

1. 每个任务闭环都要有本地提交
2. 分支命名要能表达任务本质
3. 不自动 push，除非明确需要

### 8.2 提交边界

1. 不把无关改动混进同一提交
2. 文档回环与对应实现，尽量放在同一闭环里
3. 如果工作区本来就脏，先识别哪些不是当前任务内容

### 8.3 不可做的事

1. 不用 `reset --hard`
2. 不擅自覆盖用户改动
3. 不为了“仓库干净”破坏历史现场

---

## 九、坏味道识别规范

发现以下情况时，应优先提醒并纳入当前闭环或至少明确风险：

1. 文档写旧现实，代码是新现实
2. 同一语义出现两份真相源
3. 模块职责漂移
4. API 只改实现不改文档
5. Worker / Web / Shared 协议不一致
6. archive 文档被误当主设计稿继续引用

当前项目最典型的坏味道不是函数太长，而是**历史方案和当前现实混写**。

---

## 十、与当前项目现实强相关的特殊规则

### 10.1 Agent

1. 改 Agent 时必须检查画布摘要、plan、validator、applier 是否一起保持同构
2. 不能只改 UI，不看落图逻辑
3. 不能只改后端 planner，不看前端 plan 消费协议

### 10.2 Tasks

1. 改任务系统时必须同时考虑 web 和 worker
2. 改 orchestrator 语义时必须考虑 shared 类型
3. 改 `async_tasks` 字段时必须考虑 D1 schema、cron、API、前端轮询

### 10.3 Billing

1. 改支付时必须区分“文档口径、测试口径、生产口径”
2. 任何余额变化都要能回到账本
3. 文案更新要和法务边界同步

### 10.4 Auth

1. 改身份链时不能让匿名主链失效
2. 不能把 Clerk 原始对象扩散到业务层
3. 资源归属、文件访问、API 守卫要一起看

---

## 十一、完成定义

一个任务只有同时满足下面几项，才算完成：

1. 实现闭环完成
2. 文档回环完成
3. 已验证，或已明确未验证项及原因
4. 已完成 git 留痕
5. 已说明剩余风险

---

## 十二、结论

当前项目的执行规范，本质上只是在保护一件事：

**不要让一个已经有很多真实运行时系统的项目，因为继续相信过期文档、重复造真相源、跳过回环和验证，而慢慢失去一致性。**

后续所有开发，都应该围绕这个目标执行。
