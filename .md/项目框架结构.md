## 一、文档定位

这份文档只回答三个问题：

1. 当前项目到底有哪些真实模块
2. 这些模块各自负责什么
3. 现在的主运行时链路是怎样的

它不再追求把每个目录和每个子页面都展开成巨大的树。那种写法很快会过时，而且会把“历史设计”伪装成“当前现实”。

---

## 二、项目当前定位

Nano Banana Canvas 当前是一个运行在 Cloudflare 上的 **AI 工作流画板平台**，核心不是单点模型调用，而是把以下能力收进同一个系统：

1. 可视化工作流编辑
2. 多 Provider 模型调用
3. 图片 / 视频 / 音频异步任务编排
4. Agent 辅助搭建、修改、诊断工作流
5. 账户、账单、积分、文件与公开分享链路

当前真实技术基座是：

1. `Next.js 16 + React 19`
2. `pnpm workspace + Turborepo`
3. `Cloudflare Workers + D1 + R2`
4. `Clerk`
5. `Stripe`

## 三、顶层结构

```text
/
├─ apps/
│  ├─ web/         # 主 Web 应用与绝大多数运行时逻辑
│  └─ worker/      # Cron / Workflow / 长任务运维核心
├─ packages/
│  └─ shared/      # 跨应用共享类型与常量
├─ e2e/            # Playwright 端到端测试
├─ .md/            # 项目文档与归档
├─ CLAUDE.md       # 项目级架构宪法
└─ package.json    # monorepo 根命令入口
```

### 3.1 `apps/web`

这是当前项目的**主系统**。它承载：

1. 页面路由
2. API Route Handlers
3. 画布编辑器
4. Agent 面板
5. 账户与账单 UI
6. 工作流、文件夹、Explore、视频分析
7. 计费、任务、文件访问、Webhook 接口

### 3.2 `apps/worker`

这是当前项目的**后台运维与长任务协同层**。它承载：

1. 定时任务
2. 超时与清理
3. Cloudflare Workflows 编排
4. 与 `async_tasks` 协同的后台任务能力

### 3.3 `packages/shared`

这是当前项目的**共享协议层**。它承载：

1. `TASK_CONFIG`
2. 任务类型与编排类型
3. 共享常量
4. 跨端都要一致的基础类型

## 四、Web 应用结构

### 4.1 页面层

`apps/web/app` 当前分成四类路由语义：

1. `(landing)`
   公开页面、品牌入口、定价、法务、文档说明
2. `(auth)`
   登录与注册
3. `(app)`
   工作区、Explore、Workflows、Billing、Account、Video Analysis
4. `(editor)`
   画布编辑器

这里最重要的不是完整路由树，而是职责边界：

1. 公开信息与品牌叙事在 `(landing)`
2. 身份切换在 `(auth)`
3. 业务运营与资源管理在 `(app)`
4. 高交互编辑在 `(editor)`

### 4.2 API 层

`apps/web/app/api` 当前已经是一个很重的业务核心，而不只是薄路由壳。

主要语义域包括：

1. `api/workflows`
   工作流 CRUD、发布、克隆、点赞、收藏、举报、缩略图、执行历史、Agent 审计与回放
2. `api/tasks`
   异步任务提交、查询、取消
3. `api/ai`
   同步执行、流式执行、模型列表
4. `api/billing`
   Checkout、Portal、订阅、积分包、账单入口
5. `api/credits`
   积分余额、流水、usage
6. `api/files`
   文件上传与账户级私有访问
7. `api/webhooks`
   Clerk 与 Stripe 外部事件同步
8. `api/agent`
   Agent 规划、诊断、解释、优化、模板改造、Prompt refine

### 4.3 前端组件层

`apps/web/components` 当前可以理解为七个主要模块：

1. `canvas/`
   画布容器、工具栏、控制器
2. `nodes/` 与 `edges/`
   工作流节点和连线
3. `agent/`
   右侧 Agent 面板及其提案/确认/回放 UI
4. `workspace/`
   工作区管理
5. `explore/` 与 `workflows/`
   公开内容消费与复用入口
6. `billing/`
   账单、积分、usage、Portal 操作
7. `layout/` / `profile/` / `shared/` / `ui/`
   页面骨架、账户页、共享组件、基础 UI

### 4.4 领域逻辑层

`apps/web/lib` 是当前 web 端真正的业务中枢，最值得关注的不是文件数量，而是模块分工：

1. `lib/tasks`
   异步任务真相源，编排 D1、Processor、平台计费、legacy queue 与 workflow 双轨
2. `lib/billing`
   Stripe、账本、定价、积分、订阅、Webhook、扣费与退款
3. `lib/agent`
   画布摘要、结构化 plan、校验、应用、审计存储
4. `lib/auth`
   Clerk 会话桥接与业务 actor 抽象
5. `lib/query`
   React Query 读写边界
6. `lib/validations`
   API 入参和模型 schema
7. `lib/platform-runtime`
   平台模型与供应商能力解析

### 4.5 状态层

`apps/web/stores` 当前至少有四个重要真相源：

1. `use-flow-store`
   画布节点、边、视口
2. `use-history-store`
   撤销 / 重做
3. `use-execution-store`
   执行态
4. `use-agent-store`
   Agent 会话态

当前最关键的设计原则是：

1. 工作流真相源在 `use-flow-store`
2. Agent 不能复制一份平行 workflow 状态
3. 自动保存和执行链要复用现有 store，而不是旁路写入

## 五、后台 Worker 结构

`apps/worker/src` 当前主要分成四部分：

1. `cron/`
   定时扫描、超时、清理
2. `queue/`
   传统队列消费路径
3. `workflows/`
   Cloudflare Workflows 长任务编排
4. `task-runtime/`
   任务执行桥与共享运行时

这说明当前架构已经不是早期纯 Queue 方案，也不是纯前端轮询方案，而是**双轨编排现实**：

1. 仍保留 legacy queue 路径
2. 已有 workflow 主编排路径
3. 两者围绕同一份 `async_tasks` 和共享任务内核协作

---

## 六、共享层结构

`packages/shared` 当前职责很克制：

1. 不承载重量级业务实现
2. 只承载跨端必须一致的协议与常量

当前重点内容包括：

1. 任务配置 `TASK_CONFIG`
2. `TaskOrchestrator`
3. 共享类型出口
4. 基础工具常量

这个边界是正确的。共享包越小，越不容易把前后端耦死。

## 七、当前主运行时链路

### 7.1 工作流编辑主链

```text
用户进入编辑器
→ ReactFlow 画布加载
→ use-flow-store 维护节点/边/视口
→ use-auto-save 自动保存
→ 工作流持久化到 D1
```

### 7.2 Agent 共创主链

```text
用户输入自然语言
→ Agent 面板收集上下文
→ lib/agent/summarize-canvas 提炼画布摘要
→ /api/agent/* 生成结构化计划
→ validate-agent-plan 校验
→ apply-agent-plan 落图
→ use-history-store 记录可撤销快照
→ use-auto-save 持久化
```

### 7.3 AI 执行主链

```text
用户执行工作流
→ 同步节点走 /api/ai/execute 或 /api/ai/stream
→ 异步节点走 /api/tasks
→ lib/tasks/service.ts 决定 platform/user_key 与 orchestrator
→ async_tasks 写入 D1
→ worker/queue/workflows 协同处理
→ 输出落 R2
→ 前端轮询 /api/tasks/:id 或读取执行历史
```

### 7.4 商业化主链

```text
用户访问 /pricing 或 /billing
→ /api/billing/* 发起 Checkout / Portal / 订阅操作
→ Stripe 回调 /api/webhooks/stripe
→ lib/billing/* 同步 subscriptions / billing_orders / credit_balances
→ 平台执行链复用账本做 freeze / confirm / refund
```

### 7.5 身份主链

```text
Clerk 会话
→ auth/session-actor
→ users 表镜像
→ 账户级资源归属
→ API 按匿名态 / 登录态做显式保护
```

## 八、当前架构的关键事实

### 8.1 当前不是“纯前端画板”

它已经是一个明显的**全栈工作流平台**，因为：

1. 任务编排在服务端
2. 计费在服务端
3. 账户与资源边界在服务端
4. Agent 审计与回放在服务端

### 8.2 当前不是“纯 Node 后端”

它也不是传统意义上的单体 Node 服务，而是 Cloudflare 形态的双应用：

1. `apps/web`
2. `apps/worker`

### 8.3 当前不是“设计稿状态”

以下系统已经属于运行时现实，而不是规划：

1. Agent
2. Billing
3. Clerk
4. async tasks
5. workflow orchestration

所以主文档必须把它们写成“当前结构”，而不是“未来方案”。

## 九、当前主要风险点

### 9.1 文档最容易过时的地方

1. 逐文件目录树
2. 已经完成的历史流水式更新日志
3. 早期单一路径设计稿

### 9.2 真正需要保持同步的地方

1. 顶层模块边界
2. 主运行时链路
3. 真相源位置
4. 关键职责分层

### 9.3 兼容性风险

如果后续继续按过期文档开发，最容易出的问题是：

1. 把 Agent 当成“规划中功能”重复造轮子
2. 把任务系统误判成单一路径，忽略双轨编排现实
3. 把计费和身份系统当成历史功能，绕开真实账本与 actor 边界
4. 在错误层面引入第二套真相源

## 十一、结论

当前项目结构可以用一句话概括：

**`apps/web` 负责产品主运行时，`apps/worker` 负责后台协同与长任务编排，`packages/shared` 负责最小共享协议，三者围绕 D1/R2/Clerk/Stripe/Agent/Tasks 形成一个已经在线可运行的 AI 工作流平台。**

这就是后续修订文档和避免不兼容时应该对齐的“项目现实”。
